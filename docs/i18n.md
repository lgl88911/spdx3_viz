# Translation

The UI ships in English (the source language) and Chinese. This document covers
how the two stay in sync and where each piece lives.

## Files

| File                       | What it is                                                           |
| -------------------------- | -------------------------------------------------------------------- |
| `src/i18n/en.json`         | Every translatable string, keyed by the English it renders           |
| `src/i18n/zh.json`         | The same keys with their Chinese translation                         |
| `src/i18n/index.js`        | Lookup: exact match, then number pattern, then sentence template     |
| `src/i18n/dom.js`          | Walks the rendered DOM and swaps text, tooltips, placeholders        |
| `src/app/locale.js`        | Alpine binding: `locale`, `setLocale()`, `toggleLocale()`, `t`, `tf` |
| `scripts/i18n-extract.mjs` | Rescans the source and updates both JSON files                       |
| `scripts/i18n-check.mjs`   | Fails when the catalogs disagree or a placeholder is lost            |

Because the key **is** the English string, the two files read as a side-by-side
table, and a translation can be reviewed without opening a template:

```json
{
  "No requirements to plot.": "没有可绘制的要求。",
  "{0} licenses": "{0} 个许可证",
  "No {0} in this document": "本文件中没有 {0}"
}
```

`^` both files must contain the same keys in the same order: `npm run i18n:extract`
writes them that way, and `npm run i18n:check` reports the difference.

## Three kinds of key

1. **Exact** – the string as it appears on screen: `"Functional Safety"`.
2. **Count pattern** – a fixed phrase with a `{0}` slot. Numbers are replaced by
   a placeholder before lookup, so `"{0} files"` covers `1 file`, `12 files` and
   `1,204 files`, and the captured number is pasted into the translation.
3. **Sentence template** – a fixed sentence with one or more `{n}` slots, used
   when the app assembles the sentence itself (`"No {0} in this document"`). A
   template is only built when at least two words of context survive around the
   slots, which is what keeps a short pattern from matching by accident.

Slots may be reordered in the translation. Chinese usually puts the counted
noun first, so `"{0} of {1} packages in scope"` becomes
`"范围内的 {1} 个包中有 {0} 个"`: the numbers follow their original index.

## Adding or changing copy

1. Edit the view or the JS. Write the English as it should read on screen.
2. `npm run i18n:extract`: adds any new string to `en.json` and to `zh.json`
   with an empty value, and keeps every existing translation.
3. Fill in `src/i18n/zh.json`. The value must keep the same `{n}` slots.
4. `npm run i18n:check` to confirm, then reload: the new copy switches with the
   language toggle.

If a string is produced by a template the extractor cannot see (a slot filled
from a variable), either mark it up as a sentence template in the source (write
it as one template literal with two words of context) or add it to `EXTRA_KEYS`
in `scripts/i18n-extract.mjs`.

## What is never translated

- Release notes in the changelog, marked `data-i18n-skip`.
- Anything inside `<code>`, `<pre>`, `<kbd>`, `<script>`, `<style>`: ids,
  paths, SPDX field names, sample JSON-LD.
- Names, acronyms and identifiers that are identical in both languages: the
  check script lists them, and the test in `tests/i18n.test.js` allows them only
  when they contain nothing but letters, digits and common punctuation.

## Layout

Chinese is set in a Han-first font stack and loses the letter-spacing that suits
Latin small caps; both rules live at the end of `src/styles.css`, scoped to
`html:lang(zh)`. The English UI is untouched. Because the catalogs keep the same
DOM structure and classes, a translated label inherits the size and weight of the
one it replaces: translations are kept roughly as short as the English so nothing
that fitted on one line starts wrapping.

## Canvas text

The graph, the donut chart centre and the supply-chain state diagram paint text
from JS strings. They repaint on a language switch (`refreshLocalizedPaint()` in
`src/app/locale.js`); their labels come from the same catalog through `t()`.

## Switching back

Each translated text node keeps the English it came from, and the switch back to
English restores exactly that: a round trip leaves the DOM identical, byte for
byte, and only re-runs the lookup. The record is matched against the node value
**including** its indentation, because the translation is spliced between the
spaces the template wrote; a trimmed comparison would read the Chinese back as
the source and the string would stick. `sourceOf()` in `src/i18n/dom.js` owns
that rule, and `tests/i18n.test.js` pins it.

Everything the app re-renders goes through the same pass: Alpine's own output is
English, so a rebuilt node is treated as a fresh source and translated again.

## In templates

Most copy needs nothing: the DOM pass translates what is already on screen. When
a view assembles its own string, use the helpers exposed on the component:

```html
<span x-text="tf('Grade {0}', qualityGrade)"></span>
<span x-text="tf('{0} files', rows.length)"></span>
<span x-text="tf(', updated {0}', cveAffectedGenerated)"></span>
```

`t(text)` translates one finished string, `tf(key, ...args)` also fills its
slots. Use `tf` for a sentence fragment glued to a value (the last example): the
Chinese can then put a full-width comma in front, which a plain interpolation of
the English tail could not.

## Tests

`tests/i18n.test.js` pins the contract: the catalogs hold the same keys, every
translation keeps its placeholders, counts and sentence templates resolve, a
translated node still knows its English source, and no entry is left in English
unless it is a name.
